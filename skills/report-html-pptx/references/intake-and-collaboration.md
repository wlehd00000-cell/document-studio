# 필수 질문을 보존하고 답이 있는 항목은 재사용한다

[총괄](../SKILL.md)은 현재 요청·기존 brief·지정 자료를 먼저 읽는다. 강연 논지 조사, 발표 원고, 목차와 페이지 논리 개선 등 **조판 이전 콘텐츠 작업만 명시적으로 요청한 경우**에는 이 파일 제작용 필수 질문을 일괄 적용하지 않는다. 청중·목적 등 논지에 영향을 주는 누락만 묻고, 실제 파일·조판을 요청받을 때 제작 관련 필드를 확인한다. 정식 문서 제작 또는 이미 확정된 제작 요청의 누락 값은 아래 규칙대로 유지한다. [contract](intake-contract.json)의 여섯 핵심 필드와 별도의 사용처·판형은 새 문서 제작의 필수 결정이다: **진행 방식 / 문서 종류 / 주요 독자 / 읽은 뒤 할 판단·행동 / 완성 언어 / 파일 형식**, 그리고 **사용처 / 판형·방향**. 필수 질문은 여섯 개의 별도 인터뷰를 뜻하지 않는다. 확정된 항목을 빼고 누락만 짧게 묶어 묻는다.

현재 명시값은 explicit, 유효한 기존 선택은 reused, 맥락·최신성·실제 위치가 확인된 자료의 명시 지시는 source_explicit, 항목을 특정한 위임과 이유 있는 추천은 delegated다. 이 네 상태만 필수 답변을 해결한다. 이전 assumed, 파일명, 첨부 언어, sample 수치와 모호한 단서는 확정 답변이 아니다.

## 시작과 부분 답변

먼저 무엇이 이미 해결됐는지 확인한 뒤 필요한 질문을 한 번에 제시한다. 예를 들어 모두 비어 있으면 ① 원샷/함께 진행과 문서 종류 ② 독자와 판단·행동 ③ 완성 언어와 파일 형식으로 묶을 수 있다. 일반 제작 요청도 같은 원칙을 적용하며 ‘처음 사용’ 문구를 말해야만 질문하는 구조를 만들지 않는다. 주제가 없는 첫 도움 요청은 새 문서/기존 수정/번역·윤문부터 짧게 안내한다.

사용자가 일부만 답하면 그 답을 즉시 반영하고 **남은 항목을 pending으로 유지하여 다시 묻는다**. 기존 brief의 intake.fields/missing/question_groups, 또는 파일을 만들기 전의 채팅 작업 메모를 이어 쓴다. 턴이 바뀌거나 다른 설명이 추가돼도 미응답을 삭제하지 않는다. 같은 질문 전체를 다시 보내지 않는다. 무응답·짧은 ‘좋아’·미제출 추천 선택은 답변으로 채우지 않는다.

‘대충’, ‘알아서’, ‘그냥 진행’, ‘適当に’, ‘お任せ’는 미지정 항목 전체의 위임이 아니다. ‘형식은 편집하기 편한 것으로 추천해줘’처럼 범위가 특정된 위임은 그 항목의 선택과 이유를 기록해 해결한다. ‘원샷으로’는 진행 방식만 해결한다. ‘위 질문은 모두 추천대로, 원샷으로 진행’처럼 제시된 선택 범위를 분명히 채택한 답은 해당 범위의 답변이다. 이미 확정한 선택을 다시 승인받지 않는다.

v4.2부터 사용자가 **현재 질문의 8개 항목 모두를 명시적으로 추천 위임**하는 경우, 각 필드를 `delegated_fields`에 적고 항목마다 선택값과 이유를 기록해 묶어서 해결할 수 있다. 이때 `mode`는 `choice_origins.mode`에 `user_message:turn-id:line-n` 등 **현재 사용자의 실제 위임 발화 위치**가 있어야 하며, 파일 본문이나 모델의 단독 제안은 출처가 될 수 없다. 예: “방금 제시한 진행 방식·문서 종류·독자·목적·언어·출력·사용처·판형 8개를 모두 판단해서 진행해줘.” 반면 “알아서”, “계속”이라는 모호한 표현만으로 이 배열을 만들어서는 안 된다. 권장값이 빠진 항목만 계속 pending이며, 첨부 문서끼리 상충하는 지시는 사용자의 구체적 선택 없이는 해결되지 않는다.

## 추천값과 독립 작업

원샷, 읽기용 보고서, Document Studio 담당 직원/정보 공유, 대화 언어, 편집 가능한 PPTX는 **질문에 제시할 추천 후보**다. 필수 항목이 비었다는 이유로 자동 채택하지 않는다. 진행을 멈추기 위한 종이 절차는 만들지 않는다: 답변 대기 중에는 제공 자료 읽기, 근거/자산 확인, 영향 범위 파악처럼 선택에 의존하지 않는 일을 계속한다. 미해결 선택에 의존하는 최종 집필·디자인·출력은 답변 뒤에 진행한다. 주제·필수 원본·실질적 충돌도 필요한 질문에 함께 묶는다.

읽기/발표/인쇄/기존 양식의 사용처는 명시된 목적에서 재사용한다. 실제 구도가 달라질 만큼 애매하면 종류·형식 질문에 사용처와 판형·방향을 함께 확인한다. PPTX는 판형 선택이 아니며 프로필 추천값을 자동 채택하지 않는다. 취향, 색, 창의성과 화려함은 선택 사항이며 별도 필수 설문으로 늘리지 않는다. HTML 제작→기본 HTML-to-PPTX 경로는 고정이다.

intake.py는 누락·이전 가정·부분 답변을 needs_decision으로 유지한다. 제안값은 suggestions이며 fields의 답변이 아니다. 완전한 brief의 국소 수정은 유효한 조건을 재사용하고 변경/충돌 항목만 다시 연다. 번역·윤문·작은 수정·검토된 HTML 변환·플러그인 유지보수에는 새 문서 질문을 강제로 적용하지 않는다.

## 채팅과 완성

호스트의 채팅 질문 기능 또는 짧은 번호 목록을 사용한다. [질문 후 대기](question-waiting.md)를 적용한다. 비동기 질문창을 연 뒤에는 실제 답변이나 명시적인 취소가 올 때까지 대기하며, 질문 표시 완료만 받고 곧바로 final로 턴을 종료하지 않는다. 독립 작업이 끝나면 지원되는 대기 도구로 기다리고, 대기 시간이 지나도 필수 미응답을 자동 선택·승인·완료로 처리하지 않는다. 호스트가 질문창을 유지할 수 없으면 답한 항목과 미응답을 보존해 일반 채팅으로 이어받는다. 별도 온보딩 화면·요약 확인·전송·JSON 복사는 요구하지 않는다. 답변을 직접 반영한다. 원샷은 필수 결정 해결 뒤 파일과 검수까지 끝내며, 협업 요청은 실제 원고와 상세 본문을 담은 대표 구도로 내용과 디자인을 함께 확인한다. 선택이 끝난 뒤 단계마다 추가 승인을 만들지 않는다.

실제 선택 상태와 짧은 단계별 전달은 [실행 계약](production-contract.md)을 따른다. 새 제작 전 prepare/status를 실행하고 부분 답변도 같은 brief에 보존한다. 창의성·화려함은 여전히 선택 사항이다.
