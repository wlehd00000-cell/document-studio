# 주장·근거·한일 표현의 최종 점검

새 제안/의사결정 자료 또는 주장·수치·순서·최종 문구가 바뀐 구역에 사용한다. 기존 page map, 원고, 출처와 QA 기록을 재사용한다. 단순 색/정렬 수정에 전체 문서의 논리를 다시 설계하지 않는다. 이 기준은 DEMO 조판·문체·캡션 규칙을 보완한다.

## 내용과 논리

| 확인할 관계 | 실제로 찾을 문제 |
|---|---|
| 제목 → 본문 → 그림 | 제목은 효과가 미확인이라고 쓰는데 그림은 효과 달성을 단정하는 등 같은 페이지의 결론 불일치 |
| 주장 → 근거 → 조건 | ‘충분하다’, ‘제한적이다’, ‘유일하다’ 등의 평가가 출처/비교 기준/조건보다 강함 |
| 전체상 → 본편 → 요청 | 예고한 논점·페이지 참조가 본편과 다름, 새 의미 없이 앞 페이지를 반복함, 요청할 판단의 전제가 빠짐 |
| 비교 대상 → 수치 | 단위·기간·대상·분모가 다른 값을 같은 기준처럼 비교함, 반복된 동일 수치가 다름, 합계·단계 수가 불일치함 |
| 사실 → 해석 → 제안 | 예시/시험/추정/목표를 실적으로 바꿈, 서로 다른 프로젝트 상태를 같은 완료로 씀 |

발표자료의 제목은 근거가 뒷받침하는 메시지로 쓴다. 상세 보고서/정식 계획서의 중립적 제목, 지정된 목차, 함께 읽어야 하는 문단·표·캡션은 유지할 수 있다. 차트가 핵심이면 읽어야 할 의미와 조건을 제목 또는 가까운 설명에 둔다. 모든 페이지를 결론 문장이나 좌우 두 칼럼으로 통일하지 않는다.

숫자·단위·기간·대상과 평가 근거는 원자료와 대조한다. 제목에 단계 수를 쓴 경우 실제 단계와 맞춘다. 기계 검사는 명시적으로 연결된 항목만 대조하며, 숫자가 다르게 나왔다고 자동으로 같은 수치라고 판단하지 않는다.

## 한국어·일본어 문장

최종 산출물 언어의 항목만 적용한다. 제목, 표, 그림의 같은 개념은 같은 용어를 사용한다. 약어는 독자가 알 필요가 있는 첫 등장에 정의한다. 조직/담당/대상이 생략된 ‘내부’, ‘외부’, ‘현장’, ‘당사’는 문맥에서 주체를 찾을 수 있어야 한다.

한국어는 기존 DEMO 보고서 문체와 조사/어절/수치-단위의 실제 줄 흐름을 유지한다. 일본어는 완료/진행/예정의 상태, 긴 명사 수식의 주체, 같은 계층의 문말, 관점이 생략된 상대어와 표기 혼용을 확인한다. 본문 경어와 공식 명칭은 그대로 둘 수 있다. ‘ソリューション’, ‘付加価値’ 등의 단어 자체를 금지하거나 전 문장을 常体로 바꾸지 않는다. 실제 의미가 약한 추상 표현만 근거와 동작이 드러나도록 고친다.

## 검토와 수정 기록

현재 담당자가 위 관계를 점검하고 변경/문제 구역의 실제 최종 화면을 본다. 독립 리뷰는 사용자가 요청했거나 위임이 허용되고 복잡한 주장 검토에 도움이 될 때만 사용한다. 기존 원샷/협업 모드와 확인 지점을 유지하며, 자동으로 새 채팅·리뷰 라운드·설문을 만들지 않는다.

독립 리뷰가 필요한 경우에는 현재 최종 파일과 독자/목적, 필요한 원자료만 전달한다. 제작자의 선호나 예상 결함을 주입하지 않는다. 파일 본문과 실제 화면의 확인 범위를 구분한다. 발견하지 못한 결함을 숫자 할당량에 맞춰 만들지 않는다. ‘문제 없음’과 ‘자료/화면 부족으로 확인 못함’은 다르다.

유의미한 지적만 기존 QA 기록에 `페이지/항목 · 문제와 근거 · 채택/미채택/보류 · 수정/이유`로 남긴다. [공통 상태 계약](../system/project-state.md)의 editorial/visual layer와 `blocking`/`warning` severity를 사용한다. 취향 차이와 실제 오류를 구분하고, 중요한 의미/범위 변경은 기존 사용자 결정 절차를 따른다. 수락된 수정 후에는 바뀐 내용과 관련 출력만 다시 확인한다. 수정 횟수나 70점 같은 점수는 품질의 증거로 쓰지 않는다.

## 보조 기계 검사

`scripts/check_document.py <final.html> --json`은 페이지/제목 추출, 남은 치환 문구, 명시된 단계 수, 주석으로 연결한 반복 수치와 일부 일본어 표기 혼용을 점검한다. Python 표준 라이브러리만 필요하다. 선택적 주석은 작성자가 원자료로 확인한 관계에만 붙인다.

- 단계 컨테이너: `data-enumeration="migration" data-count="3"`; 실제 단계에 `data-step-index="1"` 등을 쓴다. 컨테이너가 없으면 제목의 `3단계`/`3段階`와 명시된 단계 인덱스만 대조한다.
- 반복 수치: `data-quantity="annual-cost" data-value="120" data-unit="JPY" data-period="FY2026" data-scope="pilot" data-basis="estimate"`. 같은 quantity/period/scope/basis의 값·단위를 대조한다. 환산 단위/서로 다른 추정 시나리오에는 별도 quantity/basis를 사용한다. 값은 소수점과 천 단위 쉼표를 허용한다.
- 용어: 필요할 때만 `--terms terms.json`을 사용한다. 예: `{"groups":[["도입 검증", "도입검증"],["サーバー", "サーバ"]]}`. 서로 다른 의미로 쓰인 경우 경고를 무시하고 이유를 남길 수 있다.
- 작성 중 템플릿/예시 점검에는 `--template`을 명시한다. 완성 문서의 치환 문구 검사를 끄는 용도로 쓰지 않는다.

`scripts/check_layout.mjs <final.html> --json`은 기존 Playwright/Chromium이 있을 때 인쇄 화면에서 폰트/이미지 준비를 기다리고 네 방향 넘침, 잘린 텍스트와 푸터 충돌을 측정한다. `[data-pptx-slide]`, `.demo-page`, `.page`, `.slide`, `section.s`와 DEMO 푸터를 지원한다. 검사 페이지 0개는 실패다. 용지/글자 크기는 강제하지 않는다. 설치된 패키지 위치가 다르면 `PLAYWRIGHT_MODULE_DIR`에 playwright 패키지 또는 node_modules 경로를 지정한다. 검사 때문에 새 패키지/브라우저를 자동 설치하지 않는다.

기존 Chromium 실행 파일이 없고 설치된 Chrome/Edge를 재사용할 때에는 `GS_QA_BROWSER_EXECUTABLE`에 해당 실행 파일의 절대 경로를 지정할 수 있다. 새 설치·다운로드·시스템 설정 변경은 이 검사에 포함하지 않는다.

기계 검사의 성공은 **해당 자동 검사 통과**다. 논리·미감·사진 크롭·모든 요소 간 겹침·실제 사용 글꼴·최종 PPTX 편집 가능성을 보증하지 않는다. 브라우저 미지원/로딩 실패는 실패 또는 미확인으로 기록한다. 기존 [DEMO 최종 크기 검토](demo-esg-review.md)와 [PPTX 변환 검수](../../html-to-pptx/SKILL.md)를 계속 수행한다.

이 두 도구의 JSON은 **보조 검사 결과**이며 `project_state.py`의 완전한 automated receipt가 아니다. `FAIL`/`WARN`은 이 도구 내부의 출력 상태다. 확인된 문제를 현재 target signature에 연결한 기존 review receipt에 옮길 때는 각각 `blocking`/`warning`으로 기록하고, 문맥에 따른 오탐을 해소했으면 근거와 이유를 남긴다. 검사 성공 문구를 임의의 `passed` 플래그로 변환하지 않는다. 원본 HTML·CSS·폰트·이미지와 검사 구현의 현재 hash를 보존하고, 정식 text-flow/OOXML 검사 및 실제 visual/export 검토를 계속 사용한다. 변경된 입력은 이전 보조 검사 결과도 무효화한다.
